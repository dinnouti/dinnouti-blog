This post is a self-service cheat sheet for Python environment and version management. One of the biggest problems with virtual environments in Python is the number of tools available and how they play together.

> **Updated October 2026.** I wrote the original in 2020 with pyenv and venv. Today I use **uv** for anything new and **pipenv** for older projects, and I do not mix the two in the same project. I want a tool that gets me going quickly with no pre-work. The original pyenv content is kept at the end as a legacy section.

## TL;DR

- **New script or small project:** use `uv`. One tool installs Python, creates the environment and locks dependencies.
- **Existing project with a `Pipfile`:** keep using `pipenv`, or [move it to uv](#moving-from-pipenv-to-uv).
- **One-off tool or throwaway experiment:** `uvx` or `uv run --with`.
- **pyenv + venv:** still works, but it is two tools and more setup than I need now.

## Installing and updating the tools: Homebrew on Linux

I install the tools themselves with [Homebrew on Linux](https://docs.brew.sh/Homebrew-on-Linux), so one command keeps Python and the Python tools current:

```bash
brew install python uv pipenv
# update everything later
brew update && brew upgrade
```

Homebrew keeps the tools (uv, pipenv, and the system-level Python) up to date. The project-level Python versions still come from uv (`uv python install`) or the `Pipfile`, so each project stays pinned.

## uv

[uv](https://docs.astral.sh/uv/) is a single fast binary. It manages Python versions, virtual environments, dependencies and CLI tools, so it replaces pyenv, venv, pip and pipx for my use. Install it once (see the uv docs, or `pip install uv` inside a throwaway environment).

### Python versions

```bash
# versions found on this machine, plus the ones available to download
uv python list
# install a version (uv downloads it, no compiling like pyenv)
uv python install 3.13
# pin the folder to a version, writes .python-version
uv python pin 3.13
```

### A project

```bash
uv init                 # creates pyproject.toml, .python-version, README and src/
uv add requests         # creates .venv and uv.lock, adds the dependency
uv run python main.py   # runs inside the environment, no activate needed
uv sync                 # recreate the environment from uv.lock on another machine
```

`uv init` creates a `pyproject.toml`, a `.python-version`, a README and a `src/` package folder. The generated `pyproject.toml` looks like this:

```toml
[project]
name = "myproject"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.13"
dependencies = []
```

`uv run` and `uv sync` create the `.venv` for you and keep it in the project folder by default.

### A single script

For one file there is no need for a project. uv stores the dependencies inside the script itself ([PEP 723](https://peps.python.org/pep-0723/)):

```bash
uv add --script report.py requests
uv run report.py
```

The script now carries its own requirements:

```python
# /// script
# requires-python = ">=3.13"
# dependencies = [
#     "requests>=2.34.2",
# ]
# ///
import requests
print(requests.get("https://example.com").status_code)
```

Send someone that one file and `uv run report.py` is all they need.

### Throwaway runs and CLI tools

```bash
# run with a temporary dependency, nothing is added to the project
uv run --with rich python -c "import rich; print('ok')"
# run a CLI tool once, without installing it
uvx cowsay -t hi
# install a CLI tool permanently, in its own isolated environment
uv tool install ruff
```

### Classic venv-style workflow

If you just want a venv and pip, uv does that too, only faster:

```bash
uv venv --python 3.13
uv pip install requests
```

## pipenv

pipenv combines pip and virtualenv with a `Pipfile` and a `Pipfile.lock`. I keep using it on projects that already have a `Pipfile`.

```bash
# keep the virtual environment inside the project (.venv) instead of the home folder
export PIPENV_VENV_IN_PROJECT=1

pipenv install requests     # creates the environment, Pipfile and Pipfile.lock
pipenv run python main.py   # run without activating
pipenv shell                # or open a shell inside the environment
pipenv install              # recreate the environment from the lock file
```

The `[requires]` section of the `Pipfile` records the Python version:

```toml
[packages]
requests = "*"

[dev-packages]

[requires]
python_version = "3.13"
```

### pipenv no longer installs Python by itself

The 2020 version of this post showed pipenv offering to install a missing Python through pyenv. That only works if **pyenv or asdf is installed**. Without them, current pipenv (2026.8.0) stops with:

```text
Warning: Python 3.13 was not found on your system...
Neither 'pyenv' nor 'asdf' could be found to install Python.
You can specify specific versions of Python with:
$ pipenv --python path/to/python
```

## Moving from pipenv to uv

Moving a project is quick, and you can keep both files side by side until you are happy. I tested this on a project with `requests` and a dev dependency `pytest`.

Start from the `Pipfile`:

```toml
[packages]
requests = "*"

[dev-packages]
pytest = "*"

[requires]
python_version = "3.13"
```

### 1. Create the uv project

From the project folder, using the Python version from `[requires]`:

```bash
uv init --python 3.13
```

### 2. Add the dependencies

Add only the packages you listed in the `Pipfile`, not everything in `Pipfile.lock`. uv resolves the sub-dependencies itself and writes the lock file.

```bash
uv add requests          # from [packages]
uv add --dev pytest      # from [dev-packages]
```

The `pyproject.toml` ends up like this (the `[project.scripts]` and `[build-system]` sections that `uv init` generates are omitted here):

```toml
[project]
name = "myproject"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.13"
dependencies = [
    "requests>=2.34.2",
]

[dependency-groups]
dev = [
    "pytest>=9.1.1",
]
```

A `Pipfile` entry with `"*"` becomes a minimum version. If the `Pipfile` pins a version (`requests = "==2.31.0"`), pass it to uv: `uv add "requests==2.31.0"`.

### 3. Run it

```bash
uv run python main.py
uv run pytest
```

### 4. Clean up

Once it works, remove the old files:

```bash
rm Pipfile Pipfile.lock
rm -rf .venv     # optional, uv recreates it
uv sync          # rebuilds .venv from uv.lock
uv run pytest --version
# pytest 9.1.1
```

Commit `pyproject.toml`, `uv.lock` and `.python-version`.

### Command map

- `pipenv install` -> `uv sync`
- `pipenv install <pkg>` -> `uv add <pkg>`
- `pipenv install --dev <pkg>` -> `uv add --dev <pkg>`
- `pipenv uninstall <pkg>` -> `uv remove <pkg>`
- `pipenv run <cmd>` -> `uv run <cmd>`
- `pipenv lock` -> `uv lock`
- `pipenv --rm` -> `rm -rf .venv`

### Keeping the exact versions

If you must keep the exact versions from `Pipfile.lock` (for example to avoid any change while migrating), export them and import with `-r`:

```bash
pipenv requirements > requirements.txt
pipenv requirements --dev-only > dev.txt
uv add -r requirements.txt
uv add --dev -r dev.txt
```

This works, but every transitive package ends up in `pyproject.toml` as an exact pin with an environment marker, so the file is noisy. I prefer the clean approach above.

## Which one for what?

| I want to... | uv | pipenv |
|---|---|---|
| Install a Python version | `uv python install 3.13` | needs pyenv/asdf, or `--python <path>` |
| Create the environment | `uv venv` or automatic with `uv run` | `pipenv install` |
| Add a dependency | `uv add requests` | `pipenv install requests` |
| Run something | `uv run main.py` | `pipenv run python main.py` |
| Recreate from lock file | `uv sync` | `pipenv install` |
| Lock file | `uv.lock` | `Pipfile.lock` |
| Single-file script with dependencies | `uv add --script` | not supported |
| Run a CLI tool once | `uvx <tool>` | not supported |

## Other tools worth knowing

I do not use these day to day, but you will meet them:

- **venv / virtualenv** - the standard library baseline (`python -m venv .venv`). Every other tool builds on the same idea.
- **Poetry, PDM, Hatch** - project managers aimed at packaging and publishing libraries. Good if you publish to PyPI. uv covers the same ground with less setup.
- **conda / mamba / pixi** - the choice when you need non-Python binaries (CUDA, GDAL, scientific stacks). Pixi is the newer, faster, project-based one.
- **pipx** - installs CLI tools in isolated environments. `uv tool install` does the same.
- **Rye** - an earlier experiment by the same people. It has been folded into uv.
- **direnv** - not a Python tool, but handy to activate a `.venv` when you `cd` into a folder.

## Legacy: pyenv + venv (the 2020 approach)

Pyenv manages multiple Python versions on the same machine, but it compiles each one from source, so installs are slow and need build dependencies. Often I saw pyenv, venv and pipenv getting out of sync. The most reliable combination I found in 2020 was pyenv with venv:

```bash
# show local versions
pyenv versions
# list all versions
pyenv install --list
# install a specific version
pyenv install 3.8.7
# attach a version to a local folder, creates a file .python-version
pyenv local 3.8.7
python3 --version
# Python 3.8.7
python3 -m venv .venv
```

Python 3.8 and 3.9 are end of life now, so use a current version in new work. The `.python-version` file is the same format uv reads, so a folder set up with pyenv also works with uv.
